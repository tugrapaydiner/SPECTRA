# Iteration 07: consistent kit metadata checks

Reviewed base: `ebc7a9a2d32a33805d0f3aff808ae2e58d5699d1` in PR #48.

The kit's self-test compared source-proof dimensions with the manifest, but its
JSONL runner skipped that comparison. A complete, correctly hashed kit with a
syntactically valid manifest could therefore publish a successful result while
declaring a different input maximum or class count from the verified model. The
same kit failed its self-test. Numerical predictions still followed the actual
source model; the defect was acceptance of contradictory deployment metadata.

Both entry points now use one source-verification helper. Feature width, maximum
and class count must agree before a native session is opened or output is
published. Class-label values remain metadata from the trusted manifest; the
proof establishes numerical class indices and their count, not label provenance.

Four isolated subprocess regression cases exercise both entry points with wrong
maximum and class-count metadata. All model, source, library and input files are
intact, so inventory hashing alone cannot detect these contradictions. Before the
fix, the two runner cases failed their rejection expectations, while the two
self-test cases passed. The assembled synthetic fixture is shared without
mutation; each negative case uses its own copied kit.
